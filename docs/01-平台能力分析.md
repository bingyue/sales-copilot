## 三、支持的平台（渠道）

### 3.1 结论：只有企业微信一个平台

全量检索 `src/main/java` 与 `frontEnd/pc/src` 后确认：
- **不支持**微信公众号、抖音、小红书、钉钉、飞书、微博、网页在线客服、App、邮件、电话。
- 代码中出现的"小程序"（`Miniprogram.java`、`MiniprogramAttachmentConverter.java`）**仅是企微消息的附件类型**，不是独立接入渠道。
- 前端 `config/api.js`、`groupRobot/api.js` 中的"公众号"字样同样属于素材/消息类型，不构成渠道接入。

所有 AI 客服能力只在**企业微信「微信客服」**这一个入口生效。

### 3.2 已接入的企微能力矩阵

| # | 企微能力 | 代码位置 | 用途 |
|---|---------|---------|------|
| 1 | 自建应用（corpId / agentId / secret / token / EncodingAESKey） | `IYqueConfig` + `WxCpServiceFactory` | 全部 API 的鉴权底座 |
| 2 | **微信客服 KF** | `IYqueKfServiceImpl` | AI 客服主战场：`syncMsg` / `sendMsg` / `sendMsgOnEvent` / `getServiceState` / 转人工 |
| 3 | **会话存档 msgaudit** | `IYqueMsgAuditServiceImpl` | 拉取 + 本地解密聊天记录，供 AI 分析（需 native SDK 库路径 + 私钥） |
| 4 | 客户联系 external contact | `IYqueCustomerInfoServiceImpl` / `IYqueUserCodeController` | 员工活码、客群活码、客户/客群/标签同步 |
| 5 | 群发（客户 / 客群） | `mass/sender/{CustomerMassSender, GroupMassSender}` | 一键群发多媒体内容 |
| 6 | 朋友圈 moment | `IYqueFriendCircleServiceImpl` + `QuartzJob#jobIdToMomentId`（每小时） | 企微朋友圈发布与结果回捞 |
| 7 | 群机器人 webhook | `IYQueRobotServiceImpl` | 自动化消息推送、企业公告 |
| 8 | 事件回调 | `IYcallbackController` `/iycallback/handle` | GET 验签 + POST 事件分发 |

### 3.3 回调事件覆盖面

`IYcallbackController.handle(POST)` 目前只分发 4 类事件：

| 事件 | 处理 |
|------|------|
| `kf_msg_or_event` | → `IYqueKfService.handleKfMsg`（AI 客服入口） |
| `msgaudit_notify` | → `IYqueMsgAuditService.synchMsg`（会话存档同步） |
| `change_external_contact / add_external_contact` | → 新客入库 + 触发欢迎语/打标/备注策略 |
| `change_external_contact / del_follow_user`、`del_external_contact` | → 客户状态置为流失 / 删除 |

**未覆盖**：客户群变更（`change_external_chat`）、标签变更、通讯录变更、审批等。

## 五、AI 架构

### 5.1 模型接入层

`cn.iyque.factory.AiModelFactory` —— 配置驱动的模型工厂：

- 统一走 **OpenAI 兼容协议**：`OpenAiChatModel` / `OpenAiStreamingChatModel` / `OpenAiEmbeddingModel`
- 启动时按 `ai.models.enabled` 列表预热并缓存到 `ConcurrentHashMap`
- **默认配置：智谱 GLM-4**（`https://open.bigmodel.cn/api/paas/v4`），embedding 用 `embedding-3`（1536 维）
- 换供应商 = 改 `base-url` + `api-key`，无需改代码（任何 OpenAI 兼容端点均可）
- 支持按调用点覆盖 `temperature` / `topP`（如生成标签 0.3、朋友圈文案 0.7、通用改写 1.0）

### 5.2 RAG 链路

```
文档上传 (PDF/Word/Text)
  └─ chain/loader/ResourceLoaderFactory  →  PdfFileLoader | WordLoader | TextFileLoader
       └─ chain/split/CharacterTextSplitter        (定长切片)
            └─ chain/vectorizer/OpenAiVectorization (embedding-3, 1536维)
                 └─ chain/vectorstore/MilvusVectorStore
                      · collection: iyque_vectors
                      · 按知识库 kid 建 partition 做隔离
                      · 相似度阈值 score = 0.5

检索：IYqueKnowledgeFragmentServiceImpl.nearest(content, kid)
      → 向量召回 fragment id → 回 MySQL 取 iyque_knowledge_fragment 原文
```

数据表三件套：`iyque_knowledge_info`（知识库）/ `iyque_knowledge_attach`（原始附件）/ `iyque_knowledge_fragment`（切片）。

### 5.3 AI 客服决策流（`IYqueKfServiceImpl#handleAiBaseKf`）

```
企微 kf_msg_or_event 回调
  → 按 openKfid 查 IYqueKf；非本系统创建的客服直接丢弃
  → 用上次 cursor 调 syncMsg 增量拉取；新 cursor 落 iyque_kf_msg
  → 仅当 hasMore == 0 才处理本批消息            ★见 §7 风险 5
  → kfType=2 走排班客服；kfType=1 走 AI 客服 ↓

  ├─ externalUserId 为空 = 进入会话事件 → 用 welcome_code 发欢迎语
  └─ 有 externalUserId：按客户分组，只取每组最后一条
       → getServiceState 判断是否"人工接待中"
          ├─ 是 → 只入库，AI 完全不介入（人工优先）
          └─ 否 → 消息入库后：
               ├─ 文本消息 且 客服已绑定知识库 kid：
               │    ├─ nearest() 命中 → 拼 RAG 提示词 → 大模型生成 → 回发客户
               │    └─ 未命中 → 按 switchType 兜底：
               │         1 = 回固定文字   2 = 转人工（指定 servicer）
               │         3 = 发外部联系人二维码   4 = 大模型裸答（不走知识库）
               └─ 非文本消息 → 固定回复"不支持当前类型消息,请发送文字消息。"
```

设计要点：**人工接待状态优先于 AI**，且"知识库未命中"有四档可配置降级策略——这是该实现里最值得肯定的产品设计。

### 5.4 会话存档 AI 分析流（`IYqueMsgAuditServiceImpl#synchMsg`）

```
msgaudit_notify 回调
  → 以库中最大 dataSeq 为水位，getChatDatas(dataSeq, 1000)
  → 逐条 getDecryptData 本地解密
  → 过滤：roomId 为空（仅单聊） 且 msgType == text        ★见 §7 风险 3
  → handleMsg 入 iyque_msg_audit
  → 按 iyque_msg_rule 规则触发：
       · aISessionWarning  → 违规预审，结果入 iyque_ai_analysis_msg_audit
       · aiIntentionAssay  → 意向客户判定
```

### 5.5 对话记忆与提示词工程

| 机制 | 实现 |
|------|------|
| 记忆淘汰策略 | `strategy/HistoryEvictionPolicyManager` + 两种实现：`SlidingWindowEvictionPolicy`（滑窗）/ `SummaryEvictionPolicy`（摘要压缩），由 `ai.historyEvictionPolicy` 切换，默认 `summary` |
| 提示词管理 | `src/main/resources/prompts/role-prompts.yml` + `prompt/AiPromptManager` + `utils/PromptUtils`，外置可改 |
| 会话持久化 | `iyque_ai_conversation` + `iyque_ai_conversation_message` |
| Token 计量 | `iyque_ai_token_record`（`IYqueAiTokenRecordServiceImpl`） |
| 流式输出 | `Flux<String>`（`aiChatWithMemoryStream` / `aiNavigationChatStream`），SSE 推前端 |

## 七、能力缺口与风险（后续讨论的起点）

### 高优先级

1. **仓库中硬编码了真实密钥**
   `src/main/resources/application.yml` 明文包含智谱 API Key（已脱敏）与 MySQL `root/root`，且已提交进 git 历史。任何 fork 者都能拿到该 Key。→ 需要立刻轮换 + 改为环境变量/外置配置。

2. **纯单租户架构**
   `IYqueConfigServiceImpl.findIYqueConfig()` 直接 `findAll()` 取第一条——**整个系统只能服务一个企业微信主体**。若要做 SaaS 或多企业托管，需在数据层引入 tenant 维度并重构 `WxCpServiceFactory` 的实例缓存。

3. **会话存档只处理"单聊 + 文本 + 员工发出"**
   `synchMsg` 中 `roomId` 非空（即群聊）直接跳过，`msgType != text` 也跳过。但功能清单里存在"客群会话内容 / 客群会话预审 / AI 意向群友"——**群会话链路在开源版是不完整的**，需确认是商业版差异还是待补。

4. **AI 客服仅支持文本**
   图片、语音、视频、文件一律回"不支持当前类型消息"。缺少语音转写（ASR）与图片理解（VLM），这是「微信 AI 客服」体验上最直接的短板。

### 中优先级

5. **`hasMore != 0` 时整批消息被丢弃**
   `handleKfMsg` 中只有 `hasMore == 0` 才进入处理分支，但 cursor 已经先行落库。高并发/积压场景下会**静默丢消息**。正确做法是循环拉取直到 `hasMore == 0` 并累积处理。

6. **异常处理粗糙**
   回调链路多处 `catch (Exception e) { log.error(...) }` 吞掉异常、`e.printStackTrace()` 混用，且 POST 回调异常时直接返回加密的 `success` —— 企微不会重试，问题被掩盖。

7. **RAG 质量机制单薄**
   仅"定长切片 + 单轮向量召回 + 固定阈值 0.5"，缺少：重排（rerank）、混合检索（BM25 + 向量）、查询改写、召回引用溯源、答案兜底判据。知识库变大后准确率会明显下降。

8. **零测试覆盖**
   378 个 Java 文件、0 个测试。回调解析、加解密、RAG 检索、群发状态机这些高风险逻辑没有任何回归保护。

### 低优先级 / 架构债

9. **JPA 与 MyBatis-Plus 双 ORM 并存**，同一实体两套访问路径，长期维护成本高。
10. **定时任务用 `@Scheduled` 单机跑**（`QuartzJob`，每小时同步朋友圈），多实例部署会重复执行，缺少分布式锁。
11. **`ddl-auto: none` + 手工 SQL 包**（`configFile/scrm_push.zip`），无 Flyway/Liquibase，版本升级靠人工执行 SQL。
12. **`show-sql: true` + MyBatis `StdOutImpl` 日志默认开启**，生产环境会打爆日志。

## 八、与"典型 SCRM + 微信 AI 客服平台"的对照

| 典型平台应有能力 | 本项目状态 |
|------------------|-----------|
| 多渠道接入（公众号/小程序/App/网页/抖音/电话） | ❌ 仅企业微信 |
| 全渠道统一会话工作台 | ❌ 无坐席工作台，依赖企微原生客户端 |
| AI 自动应答（RAG） | ✅ 有，仅文本 |
| 人机协同 / 转人工 | ✅ 有（会话状态判断 + 指定 servicer 转接） |
| 排班与工作时间 | ✅ 有（排班客服 `kfType=2`） |
| 多模态（语音/图片） | ❌ 无 |
| 会话存档与质检 | ✅ 有（企微 msgaudit + AI 预审），群聊链路不全 |
| 知识库运营（版本/审核/命中分析） | ⚠️ 仅基础 CRUD + 向量化 |
| 客户旅程 / 自动化 SOP | ⚠️ 仅活码触发的欢迎语/打标/备注策略（`strategy/callback/*`），无完整旅程编排 |
| 数据看板 | ⚠️ 有渠道统计、热词分析、投诉统计，无全链路漏斗 |
| 多租户 SaaS | ❌ 单租户 |
| 工单系统 | ❌ 无（只有投诉管理） |

## 九、可讨论的下一步方向

1. **补齐 AI 客服多模态**：语音转写 + 图片理解，直接提升可用性上限。
2. **修复消息丢失与群会话缺口**：`hasMore` 循环拉取；打通群聊存档链路。
3. **RAG 质量升级**：混合检索 + rerank + 引用溯源 + 无答案兜底。
4. **配置与密钥治理**：密钥外置、轮换、`application.yml` 脱敏。
5. **多租户化**：若目标是做平台而非自用工具，这是最大的一次重构。
6. **接入第二个渠道**（公众号或网页在线客服）：验证当前架构的渠道抽象能力——目前 `IYqueKfService` 与企微强耦合，需要抽出 Channel 适配层。
